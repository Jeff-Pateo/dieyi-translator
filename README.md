# 双语助手 · 网页双语对照翻译

一个 Chrome 扩展（Manifest V3）：**自动判断当前打开的是什么语言，然后在每一段原文下方并列显示译文。**

不是整页替换，也不是弹窗翻译——是「原文和译文同时可见」的对照式阅读。英文技术文档、日文公告、德文合同这类场景下，能同时保留原文的准确表述和中文的理解速度。

**41 种语言任意互译**（默认英 → 中，也可以中 → 英、日 → 韩、简 → 繁），四种引擎可选（Chrome 内置本地模型 / Google / DeepL / OpenAI 兼容接口），并带一层**术语表 + 不可译片段保护**来解决「URL 被翻掉」「同一个术语三种译法」这类准确性硬伤。

## 一、安装

1. 打开 `chrome://extensions/`
2. 右上角打开 **开发者模式**
3. 点 **加载已解压的扩展程序**，选择本目录 `bilingual-translator-ext`
4. 打开任意英文网页：页面右下角出现**常驻的翻译开关**。     
   **默认不自动翻译**——点开关上的「翻译此页」（或弹窗里的「立即翻译」、右键菜单、快捷键）开始翻译；     
   想恢复「打开页面即自动翻译」，在弹窗或设置页打开「自动翻译」开关

### 页内开关

页面右下角那个常驻的小胶囊就是它。它只回答一个问题：**点一下会发生什么。**

```
【未翻译】                              【已显示译文】
┌─────────────────────────┐             ┌─────────────────────────┐
│ 译   翻译此页        ⋯  │             │ 中   显示原文        ⋯  │
└─────────────────────────┘             └─────────────────────────┘
  │      │            │                   （整块变成实心品牌蓝）
  │      │            └── 更多命令（常显，不是 hover 才出现）
  │      └─────────────── 动作词：告诉用户点了会做什么
  └────────────────────── 图标 = 目标语言标记（翻成日语是「日」，翻成英语是「EN」）
```

| 操作          | 结果                                                  |
| ----------- | --------------------------------------------------- |
| 点主按钮        | 开关**本页**翻译。**不改动设置页里的总开关** —— 在某个页面临时关掉，不会让其他标签页跟着停 |
| 点 ⋯         | 展开菜单：**本网站不再自动翻译 / 打开设置… / 隐藏这个按钮 / 收起为圆点**         |
| 按住拖动        | 拖到顺手的位置，松手后吸附到最近的左 / 右边缘；位置会记住                      |
| Tab / Enter | 主按钮与 ⋯ 都可键盘到达；菜单是 `role="menu"`，`Esc` 逐层收起，点空白处收起   |

三处刻意的设计决定：

- **文案写成动作，不写状态。** 旧文案是「翻译」/「已译」——「已译」是个形容词，    
  用户看到它不知道该不该点、点了会发生什么，这正是「不易察觉如何使用」。    
  改成「翻译此页」/「显示原文」之后：关闭态告诉用户「点了我能做什么」，    
  开启态告诉用户「点了你会看到什么」—— 后者还顺手回答了用户最担心的事，    
  点了不会把译文删掉，只是回到原文。
- **图标就是目标语言标记。** 多语言互译下，「翻译此页」这四个字不包含「翻成哪国话」，    
  所以图标位直接显示目标语言：`中` / `繁` / `EN` / `日` / `한`。
- **副操作常显。** 藏起来的功能等于不存在。代价是常驻宽度多 20px，    
  换来的是「一眼就能看见它还能干什么」。

首次使用时，会从按钮旁边弹出一枚**一次性引导气泡**，点名当前的目标语言  
（「点左边那颗按钮，就能把本页翻成**简体中文**」）。点「知道了」或点主按钮后记入存储，不再打扰。

三态在**颜色、图标、文案**三条通道上同时区分（未翻译 = 素色描边 + `翻译此页`、  
翻译中 = 蓝色脉冲点、已显示译文 = 实心品牌蓝 + `显示原文`），并在按钮上暴露 `aria-pressed`。

控件整块关在 **Shadow DOM** 里：站点样式进不来、我们的样式出不去，因此不必在别人的样式表里  
抢优先级。宿主走 `position: fixed` 不进文档流，同时打上 `data-ct-skip` 与 `translate="no"`  
两道标记 —— 确保**控件上那个「译」字不会被自己的翻译引擎当正文采集并翻译**（自噬）。

设置页的「翻译与显示 → 页内开关」分组可以整个隐藏控件（隐藏后工具栏图标、右键菜单、快捷键  
照常可用，**扩展本身不受影响**）、设为默认收起、以及开启**按站点记忆**  
（在某站点关掉翻译后，下次打开该站点仍是关的）。

> 想挪回右下角？设置页「页内开关 → 恢复默认位置」。>   
> 与站点自己的浮层（回到顶部、客服气泡、Cookie 条）撞车时，控件会自动上移避让。

### 装完不用刷新

扩展会在安装 / 更新时**主动把内容脚本补进所有已经打开的网页**，所以：

- 装好之后切回那些本来就开着的英文标签页，**不刷新页面**就会开始翻译；
- 从旧版本**升级**上来也一样 —— 升级前打开的标签页会自动被新版本接管，不会卡在旧状态。

这两件事分别对应后台的 `reinjectAllTabs()` 与注入守卫 `content/guard.js`，  
细节与「为什么少做一步就等于没做」见第七节末尾的**注入生命周期**。

> **想让扩展在本地 HTML 文件上也生效**：在 `chrome://extensions/` 里点本扩展的「详情」，>   
> 打开 **允许访问文件网址**。

**加载时不需要任何构建步骤。** Chrome 只会读取 `manifest.json` 直接或间接引用的那些文件  
（清单、后台、注入脚本与样式、弹窗、设置页）；`tools/`（测试与基准）与 `docs/`（设计说明）  
是开发期资料，加载时会被自动忽略。  
如果要用 `chrome://extensions/` 的「打包扩展程序」生成 `.crx`，请**先删掉这两个目录**，  
否则它们会被一起打进包（体积主要在 `tools/bench-results/` 的基准数据）。

## 二、四种翻译引擎

在扩展的**设置页**里切换。设置修改后立即生效，不用刷新页面。

| 引擎                | 是否需要 Key | 特点                              | 建议场景            |
| ----------------- | -------- | ------------------------------- | --------------- |
| **自动**（默认）        | 否        | 优先用 Chrome 内置本地模型，不可用时降级 Google | 大多数人用这个就行       |
| **Chrome 内置模型**   | 否        | 完全本地运行，内容不出本机，免费无额度；中文表达略生硬     | 翻译内部文档、含敏感信息的页面 |
| **Google 翻译公开接口** | 否        | 覆盖语种最广，速度快；属于公开接口，并发过高会被限流      | 日常快速浏览          |
| **DeepL**         | 是        | 中文表达最自然的一档；免费版每月 50 万字符         | 需要译文质量的正式材料     |
| **OpenAI 兼容接口**   | 是        | 可按提示词约束术语一致性；按 token 计费         | 专业术语密集的领域文档     |

内置模型需要 **Chrome 138 及以上**，首次使用某个语向时要下载语言包（几十 MB）。  
设置页有「下载语言包」按钮可以手动触发。

设置页底部的 **测试当前引擎** 会真的翻一句话回来，用来确认 Key 和网络是否正常。

## 三、三种显示方式

| 模式             | 效果                     | 代价                |
| -------------- | ---------------------- | ----------------- |
| **原文下方双语**（默认） | 译文追加在原文之后，插入点按容器类型自动选择 | 段落自身会变高（下方双语无法避免） |
| **仅显示译文**      | 段落内容整体替换为译文            | 会丢掉原文里的行内链接；可一键还原 |
| **悬停查看**       | 页面保持最干净，鼠标移到段落上才浮出译文   | 不能通读，适合快速扫读       |

> 模式名里刻意不写「中文」。目标语言有 41 种可选，`en→ja`、`zh→en` 这些语向下>   
> 「只显示中文」「悬停查看中文」就是错的 —— 用户看到的是日语却被提示「悬停查看中文」。

弹窗和设置页都能切；快捷键 `Alt+Shift+Y` 循环切换。

### 译文长什么样：默认「素净」

| 样式         | 效果                                                                         |
| ---------- | -------------------------------------------------------------------------- |
| **素净**（默认） | 不加边框、不加背景、不加「译」标记，只把字号调小、透明度降到 0.82，颜色取 `inherit` 跟随页面。深色页、品牌色底、图片背景上都不会糊掉 |
| **标注**     | 左侧一条竖线 + 淡色「译」标记，一眼能区分原文与译文。代价是这两样装饰本身就是对页面外观的改动                           |

默认之所以是素净：**装饰本身就是「改变页面」**。一个「译」字标记加一条色条，在整页每一段上重复几百次，就已经不是「保持原样」了。

### 「原文下方双语」把译文插到哪里

这一项直接决定页面会不会「变样」。默认的**智能分流**按宿主的实际排版方式选择插入点：

| 宿主                                                    | 插入点                                   | 为什么                                      |
| ----------------------------------------------------- | ------------------------------------- | ---------------------------------------- |
| 普通块（`<p>` / `<div>` / `<li>` / `<td>`…）               | **单元内部末尾**                            | 不新增兄弟节点，容器子项数、`:nth-child`、`p + p` 全不受影响 |
| **内联级元素**（`inline` / `inline-block` / `inline-flex`…） | **内联译文**跟在原文之后                        | 块级译文会直接打断行盒 —— 标签行被拆成两行、定高的 pill 被撑成两截   |
| **横向弹性容器自身**（`display:flex` + 行方向）                    | 可换行 → 内部追加并**独占整行**；不可换行 → **插到容器之后** | 直接追加会被当成新的弹性项，原有子项被平分掉宽度                 |
| 纵向弹性容器 / 网格容器                                         | 单元内部末尾                                | 本来就只是往下加一行，原有子项不受影响                      |
| 绝对定位元素                                                | 单元内部末尾                                | 已脱离文档流，追加进去不会推动任何兄弟节点                    |

`<td>` / `<li>` / `<dt>` 这类容器**永远内部追加**，与设置无关 —— 它们插兄弟节点会直接破坏 HTML 结构。

设置页的「译文插入方式」可以把这一项强制成 `inside`（总是内部追加）或 `sibling`（总是插到之后），用于对照与排障；`sibling` 的代价是父容器子项数翻倍。在 2500 块合成页上，`sibling` 有 **1475 / 2250** 个单元的 `previousElementSibling` 发生变化（相邻兄弟关系被打断），`inside` 与 `auto` 都是 **0**。

### 译文字号怎么算

译文大小 = `min(相对原文的比例, 页面正文基准字号)`。

两条都要，缺一不可：

- **相对原文的比例**（默认 80%，设置页可调、拖动即时生效）让正文段落里的译文「小一号」。
- **页面基准字号封顶**是为了标题。百分比字号是相对**父元素**解析的：译文插进 `<h1>` 之后，父元素就是那个 32px 的标题，光写比例会让译文也变成 30px 左右，整页视觉重量直接翻倍。封顶之后，`<h1>` 与 `<p>` 下的译文最终停在同一个字号上。

基准字号读一次 `body` 的 computed `font-size` 并按 11–18px 钳制；整页只读这一次，不随单元数增长。

## 四、多语言互译

**41 种语言，任意方向。** 源语言与目标语言各是一枚下拉，中间一枚 `⇄` 互换按钮：

```
弹窗 / 设置页
┌─────────────────────────┬────┬─────────────────────────┐
│ 自动检测（推荐）      ▾ │ ⇄  │ 简体中文              ▾ │
└─────────────────────────┴────┴─────────────────────────┘
```

| 场景          | 怎么用                                           |
| ----------- | --------------------------------------------- |
| 英文 → 中文（默认） | 源语言留「自动检测」，目标语言选「简体中文」                        |
| 中文 → 英文     | 点 `⇄` 互换；目标语言的**图标会跟着变成 `EN`**，一眼能看出点下去会翻成哪国话 |
| 日文 → 韩文     | 源语言选「日语」、目标语言选「韩文」。源语言只在检测明显不对时才需要手动指定        |
| 简体 → 繁体     | 目标语言选「繁体中文」。**简繁被当成两种不同语言**，所以在简体页面上这一格是真会生效的 |

语言表（`shared/constants.js` 的 `CT.LANGS`）是**单一数据源**，同时供三处使用：源语言下拉、目标语言下拉、  
译文块左上角那个小标记。每条都带一个 `mark` 字段 —— 中文用单字（中 / 繁），拉丁与西里尔用两字母大写（EN / RU），  
其他用母语首字（日 / 한 / ไทย）。这个标记就是页内开关图标位上显示的东西，也是「标注」样式里译文左上角那个字。

### 简繁这一格为什么需要单独判

「源语言 = 目标语言 → 整页跳过」这条判据在简繁上会出问题：一个简体页面把目标设成繁体中文，  
两边都被归一化成 `zh` 家族，于是**永远不翻**。

所以正字法（script variant）被单独判一次，用的是**严格口径**：

```
源 ≠ 目标                        → 要翻        （en → ja、ja → en、zh → zh-TW 都走这条）
源 = 目标 且都是中文：
    页面正字法 ≠ 目标正字法      → 要翻        （简体页配「目标繁体」走这条）
    页面正字法 = 目标正字法      → 不翻
    正字法无法判断（unknown）    → 不翻        （避免整页白跑一趟）
源 = 目标 且非中文               → 不翻
```

正字法判定不做完整映射表（那是一本字典），只取一批**只在某一侧出现**的高频字投票：

```js
CT.VARIANT_PAIRS = [['們','们'], ['這','这'], ['個','个'], …];  // 120 对
```

写成「成对」的形式是有原因的：手写两条字串时极容易一侧多一个、另一侧少一个，  
那种失衡**不会报错**，只会让判定悄悄偏向一侧。所以 `selftest.mjs` 把四条不变量钉死：  
两侧等长、各自无重复、**两侧无交集**（一个既当简体锚点又当繁体锚点的字会给两边同时投票，  
把判定稀释成随机）、以及没有「简繁同形」的废对（`面/面` 这种两侧同形，放进来只会稀释判定）。

## 五、译文准确性

「部分翻译不正确」里有一大类不是引擎水平问题，而是**送进引擎的东西本身就不该被翻**。  
`shared/protect.js` 在送翻前把这类片段摘出来换成占位符，返回后再还原：

```
原文 A ──protect──▶ 掩码文本 A′（片段换成私用区占位符 U+E000/U+E001）
     └─▶ 引擎 ─▶ 译文 B′
               └─restore──▶ 译文 B（占位符还原成原始片段或指定译名）
```

这样对**所有引擎**都成立 —— Google 免费接口无法注入提示词，DeepL 也不支持术语表参数，  
但两者都**不会改写私用区字符**（字体里通常没字形，tokenizer 把它当噪声原样透传）。

### 保护哪些片段

| 类别         | 例子                                      | 不保护会怎样                 |
| ---------- | --------------------------------------- | ---------------------- |
| URL        | `https://example.com/a?b=1`             | 译文里冒出「用户/个人资料」这类被翻过的路径 |
| 邮箱         | `john.doe@example.com`                  | 同上                     |
| 模板占位符      | `{{user_name}}` · `${count}` · `{name}` | 变成「{名称}」，渲染时直接丢值       |
| printf 占位符 | `%s` · `%1$s`                           | 同上                     |
| 版本号 / 型号   | `v1.2.3-beta` · `V2`                    | 变成「v1.2.3版本」           |
| 颜色 / 长哈希   | `#a1b2c3` · `9f8e7d6c5b4a3210`          | commit 号被翻             |
| 文件名 / 路径   | `app.js` · `src/utils/helper.js`        | 粘回代码就报错                |
| 标识符        | `USER_ID` · `getUserById` · `user_name` | 变成「通过ID获取用户」           |
| 术语表命中的词    | `Prompt` → `提示词`                        | 同一页里同一个词有三种译法          |

**全部要求高精确率而不是高召回**：漏保护一个 URL 只是不够好；误保护一个正常词会让那个词永远不翻，  
症状更明显也更难解释。所以每一条都要有明确的「形状」，不靠猜。这条纪律也直接决定了两个刻意的取舍：

- **单斜杠的「词/词」不当路径。** `input/output`、`and/or`、`client/server` 在英文技术文里极常见，    
  它们该被翻译；真正的路径几乎不会只有一个斜杠。所以路径模式要求**至少两个斜杠**。
- **只保护文件名，不保护它的前缀目录。** `folder/file.txt` 里只有 `file.txt` 会被摘出。

### 三条还原纪律

还原这一侧比保护更危险，因为它会**静默地越修越错**：

1. **正则必须要求至少一个哨兵在场。** 写成 `OPEN? 编号 CLOSE?` 看着更宽容，实际是灾难：     
   译文里本来就有普通数字（「第 1 章」「3 个步骤」），那个 `1` 会被当成占位符 #1，     
   整段文字被替换成表里某个片段 —— 而用户只会觉得「引擎乱翻」。     
   所以只认两种形式，**都要求哨兵在场**：`OPEN 编号 CLOSE`（标称）与 `OPEN 编号`（缺尾，引擎吞了一个不可见字符）。
2. **还原失败绝不让哨兵泄漏给用户。** 编号越界时把整段占位符**连同它的编号一起**抹掉     
   （只清哨兵会留下 `链接 z` 这种无来由的乱码），然后退回原文片段；宁可少一段内容，也不能出现控制字符。
3. **占位符数量必须守恒。** 送出去几个就该还原回几个；对不上说明引擎合并或拆分了条目，     
   这一条**不进缓存** —— 否则一次错译会被缓存长期粘住。计数同样要求哨兵在场，否则会把译文里所有数字都数成占位符。

`tools/test-protect.mjs` 用 100 项断言把这三条钉死，其中「译文里的普通数字不能被当成占位符」  
是一条**反证式**断言：如果正则写宽了，`第 1 章` 会变成 `第 https://a.com/x 章`，测试立刻红。

### 术语表

设置页「译文质量 → 术语表」，一行一条，`=` 分隔：

```
Prompt = 提示词
Function Calling = 函数调用
Kubernetes =
# 以 # 开头的行是注释
```

右侧**留空表示该词保持原文不翻译**（适合 `Kubernetes`、`OAuth` 这类不宜意译的专有名词）。  
含拉丁字母的术语按「整词 + 忽略大小写」匹配，避免 `Go` 命中 `Google`；纯 CJK 术语直接子串匹配。  
较长的一条优先命中，否则 `User` 会先吃掉 `User ID` 的前半。

命中之后这些词会走同一条占位符通道，因此**换引擎也不会变译法** —— 这正是「同一页里同一个术语译法一致」的实现方式。

> 关掉「自动保护」只会停掉不可译片段的保护，术语表仍然生效（两项独立）。

### 内置术语基座与场景识别（v1.7.2）

设置页「译文质量 → 内置术语基座」默认开启：94 条内置术语（招聘 / 产品 / 技术 / 商务 /  
专有名词五域，可在设置页分域关闭），用户术语表**永远优先**。基座升级  
（`TERMINOLOGY_VERSION` 提升）会让旧译文缓存整体失效重译。

多义单词靠**场景识别**消歧（`shared/scene.js`）：页面 URL / 标题强信号或正文  
≥4 个不同招聘关键词命中时判定为「招聘场景」，此时 `Apply→申请`、`Executive→高管`、  
`Senior→高级` 等场景限定条目才生效；无场景信息时它们不出场（普通页面里的  
Apply 仍是「应用」）。场景随翻译请求携带并参与缓存键 —— 招聘页与非招聘页缓存自然分流。

整行标签（如职位卡的 `Executive Design Sys Admin…`）会被识别为「标签串接形态」，  
以 `/` 重建边界后送翻 —— 引擎译文保留分隔，不再是连成一串的「执行设计系统管理员…」。

已知品牌名（GiveWell / Sticker Mule / Harper / Magic Eden / RemoteOK 等）内置「保持原样」，  
不会被意译；用户术语表可继续追加。

## 七、工作原理

```
                    ┌──────────────────────────────────────┐
   页面 DOM  ──────▶│  content script（注入到页面）        │
                    │                                      │
                    │  guard.js      注入守卫（版本+存活）  │
                    │  detector.js   识别语言 / 判定可译性  │
                    │  renderer.js   采集单元 / 注入译文    │
                    │  toggle.js     页内常驻开关（Shadow） │
                    │  content.js    流水线 / 观察变更      │
                    └───────────────┬──────────────────────┘
                                    │ chrome.runtime.sendMessage
                                    │ (只传文本，不传 DOM)
                    ┌───────────────▼──────────────────────┐
                    │  service worker（后台）               │
                    │                                      │
                    │  service-worker.js  消息路由/并发/缓存 │
                    │            └─ onInstalled 主动补注入   │
                    │  providers.js       引擎适配层        │
                    │  cache.js           持久化译文缓存     │
                    └───────────────┬──────────────────────┘
                                    │
              ┌─────────────┬───────┴───────┬─────────────┐
        内置本地模型    Google 接口      DeepL        OpenAI 兼容

  两侧共享（同一份 UMD 文件，content 与 service worker 各自加载）
  ┌──────────────────────────────────────────────────────────────┐
  │  shared/constants.js   语言表 / 模式 / 默认值 / 整页翻译判据    │
  │  shared/protect.js     不可译片段掩码 + 术语表（纯字符串函数）  │
  └──────────────────────────────────────────────────────────────┘
```


三个关键设计决定：

**1. 翻译单元是「叶子块」，不是文本节点。**  
`<p>Hello <a>world</a></p>` 只产生**一条**译文，而不是两条。做法是把「不含任何块级子元素的块级元素」定义为翻译单元。

**2. 页面侧不碰网络，网络侧不碰 DOM。**  
注入脚本只负责按段落收集文本、把译文插回去；所有翻译请求、缓存、并发控制都在后台。这样页面侧足够轻，不容易和站点脚本打架，缓存也天然是跨标签页共享的。

**3. 插入点按宿主的 computed display 分流，而不是全局一条规则。**  
早先两种全局策略都各有一半场景是错的：一律插成兄弟节点，代价全落在父容器上（子项数翻倍、`:nth-child` 错位、`p + p` 失效，`display:flex` 的标签行直接被挤变形）；一律追加进单元内部，则在横向弹性容器与内联级宿主上翻车（译文变成弹性项被平分宽度、或把行盒打断）。

只看标签判断不出来 —— `<div>` 既可能是普通块，也可能是弹性行容器。所以读一次 `getComputedStyle(el).display` 并按上表分流。这个读取**全部发生在采集阶段**（纯读，不会让自己的写入使样式失效），结果缓存进 `WeakMap` 供后续轮次复用：整轮最多触发一次样式重算，实测 2.8 ms，摊到 2500 块页面上可以忽略。取舍与实测数据见第六节、第九节。

### 4. 注入生命周期：为什么「装完不用刷新」不是自动成立的

Chrome 的默认行为是：`content_scripts` **只在页面加载时注入**。也就是说扩展刚装好、或者  
刚更新到新版本，那些**已经开着**的标签页里根本没有内容脚本 —— 不刷新就永远不会翻译。

这一侧的缺口需要**同时**补上两处，只做一处等于没做：

| # | 位置                             | 问题                                                                                                                                            | 做法                                                                                                                          |
| - | ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| ① | `background/service-worker.js` | 原来没有 `chrome.tabs.query`，`onInstalled` 只注册右键菜单、读设置、开欢迎页 —— **补注入链路只能被用户主动点（弹窗 / 右键 / 快捷键）触发**，装完不点就什么都不会发生                                    | `onInstalled`（install 与 update 都算）里主动 `tabs.query` 出全部 http/https 标签页，对**已加载完成**的页面逐页 `sendMessage`，失败则走 `executeScript` 兜底 |
| ② | `content/content.js`           | 顶部守卫是裸布尔 `if (window.__CT_BOOTED__) return;` —— 扩展**更新**后再注入，旧标记还活着，新脚本被自己上一次留下的标记拦在门外；而旧实例的 `chrome.*` 上下文已被更新作废，什么也做不了。页面于是**永久卡死**，不自愈、不报错 | 守卫换成「**版本号 + 存活探测**」（`content/guard.js`）：同版本且旧实例仍存活才跳过，否则先请旧实例退场（调它登记的 `__CT_TEARDOWN__`）再接管                                |

**第二处比第一处隐蔽得多**：补注入明明成功了，症状却和「根本没修」一模一样 ——  
排查时看到的是「覆盖率 100% 但页面仍是英文」，很容易误判成注入链路坏了。

退场时**刻意不清理已经渲染的译文块**。那些译文是页面上的有效内容，清掉会让用户先看到一次  
「译文消失 → 再出现」的闪回；`renderer` 的还原逻辑本来就带类名兜底，能识别并管理这些  
「不是本实例登记的」译文块。只清徽标与悬停浮层 —— 它们是瞬时 UI，脱离实例后只会变成垃圾。

**两道防自噬闸门**：页内开关的宿主同时带 `data-ct-skip` 与 `translate="no"`  
（`detector.js` 的 `shouldSkipElement` 原生支持这两个属性），而 `content.js` 的  
`isOwnNode()` 白名单也登记了 `ct-toggle`。任一失效都不会把控件上那个「译」字送去翻译。

> 真机验证路径：安装旧版 → 打开几个英文页面 → 用 `chrome://extensions/` 的「重新加载」>   
> 模拟升级 → 切回那些页面，**不刷新**，观察是否自动开始翻译（`__CT_BOOTED__.version`>   
> 应当已变成新版本，且 `__CT_TEARDOWN__` 不指向已失效的旧实例）。

### 5. 裁切容器：让译文根本不进入会被裁掉的子树

站点把内容藏起来主要用两种手段，它们**都不会有任何可见的报错**，只会让译文凭空消失：

| 手段   | 典型写法                                                                | 症状                                                  |
| ---- | ------------------------------------------------------------------- | --------------------------------------------------- |
| 行数截断 | `display:-webkit-box` + `-webkit-line-clamp: 3` + `overflow:hidden` | 译文被追加到容器末尾，正好落在被截掉的那一段里 —— 用户看到「原文末尾一个省略号，译文一个字都没有」 |
| 固定高度 | `overflow:hidden` + `max-height`                                    | 同上；而且站点自己的「展开全文」按钮往往也不再出现                           |

第二种症状更隐蔽：站点判断「要不要显示展开按钮」的依据通常是 `scrollHeight` 与 `clientHeight`  
的比较。译文块被追加进去之后，那两个量都变了，站点的判断跟着变 —— 于是**既看不全，又找不到按钮**。

判定要求 `overflow` 是 `hidden`/`clip` **并且**（`-webkit-line-clamp` 有效 **或** `max-height > 0`）。  
只写 `overflow:hidden` 而没有尺寸限制的容器**不算**裁切容器 —— 它只是不让溢出可见，内容照样排得开。

判完之后分三条路：

```
unit 在零高度折叠区（max-height:0）里   → collapsed，直接不翻。等用户展开时 MutationObserver 重扫
unit 在裁切容器里                        → 插到【最外层】裁切容器之后（reason: 'clipped'）
<tbody>/<tr>/<select> 收不下块级兄弟     → 就地追加（reason: 'clipped-degraded'），宁可看不全也不能破坏结构
```

**为什么必须取最外层**：套两层非常常见（外层 `max-height` 折叠整块、内层 `line-clamp` 截摘要）。  
挂在里层仍然会被外层裁掉。

**为什么这一条优先于用户的「插入方式」设置**：用户把插入方式设成「总是内部追加」是为了对照排障，  
而这里被裁掉的是**译文本身** —— 用户根本看不到东西，也就谈不上对照。唯一的例外是硬约束：  
`<td>` / `<li>` 里插不了兄弟节点，即使被裁切也只能就地追加，否则译文会挂到表格外面、归属完全错乱。

这个分支**此前从未生效过**，原因是守卫条件写反了：

```js
// ✗ 恒为 false —— safeAnchor 一路向上走，返回的锚点必然是 el 的祖先，
//   祖先当然 contains(el)，于是每次都退化到 inside
if (clipAnchor !== el && !clipAnchor.contains(el)) { … }

// ✓ 判据应该是「插不插得进去」，不是「谁包含谁」
if (canInsertAfter(clipAnchor, el)) { … }   // 锚点的父容器得收得下块级子元素
```

真机基准（`tools/bench-layout.html`，三组裁切夹具 × 3 份）现在能量化这件事：  
`rescuedFromClip = 6`、落在裁切子树里的译文 `clippedTrans = 0`、零高度折叠区里 `collapsedTrans = 0`。

## 九、性能

### 实测数据

在真实 Chrome（无头模式）上用合成页面测量，取多轮最小值。  
页面规模 2500 块 / 5401 个元素 / 2250 个翻译单元：

| 环节          | 优化前     | 优化后     | 变化                    |
| ----------- | ------- | ------- | --------------------- |
| 采集（首屏整页）    | 43.6 ms | 21.9 ms | **−50%**              |
| 采集（已译状态重扫）  | 43.4 ms | 23.8 ms | **−45%**              |
| 文本可译性判定     | 19.1 ms | 3.5 ms  | **−82%**              |
| 语言判定        | 15.2 ms | 8.9 ms  | **−41%**              |
| 渲染 2250 段译文 | 16.3 ms | 11.7 ms | **−28%**（单次采样，噪声大，见下） |
| 还原并重渲染      | 23.5 ms | 15.3 ms | **−35%**（同上）          |

翻译单元数量、还原后的 DOM 一致性两项在优化前后完全一致（数据存于 `tools/bench-results/`）。

> **关于渲染 / 还原两行**：它们原本是 `timeIt(fn, 1)` —— 单次采样，里面混着样式首次失效、JIT 预热、GC 这些一次性成本。后来给「插入方式」做同口径对比时才发现这两行的差值相当一部分是噪声。下面那组同进程交替测量的数据才是可信的。

### 同口径对比：插入方式与字号变量的成本

跨轮次比对不可靠，所以 `bench.html` 把两种插入方式放在**同一进程内交替测量**（`inside` → `sibling` → `inside` → `sibling`，各跑 5 次取最小值，两边面对同一台机器、同一份堆、同一个页面）。基准页也挂上了 `content/content.css`，否则渲染成本会比真实情况偏轻。

这个交替序列的用处不只是取最小值 —— **它本身就是噪声的度量**：如果同一个方式在前后两轮里就差了 2 ms 以上（这台机器上偶尔会发生），那么两个方式之间的差值就不值得解读。近期两次运行的读数：

| 指标               | `inside`       | `sibling`      | 结构不变量                                       |
| ---------------- | -------------- | -------------- | ------------------------------------------- |
| 渲染 2250 段（第一次交替） | 14.6 / 14.0 ms | 14.9 / 17.2 ms | `inside` **0** / `sibling` **1475**（共 2250） |
| 渲染 2250 段（第二次交替） | 14.1 / 14.2 ms | 14.1 / 14.4 ms | 同上                                          |
| 还原并重渲染           | 15.5 / 15.9 ms | 14.8 / 15.1 ms | 同上                                          |

两次交替里 `inside` 与 `sibling` 的差值是 **+0.3 / ±0 ms**，量级远小于运行内抖动。结论不是「某个方式更快」，而是：**插入点的改动在渲染成本上基本不花钱**（差别在噪声内），而结构不变量上的差别是 **0 : 1475** —— 一个是零，一个打断三分之二段落的相邻兄弟关系。这笔账显然划算。

其中「写字号变量」原本占了大头，单独拆出来测（`refreshFontScale` 对每个节点重跑一遍）是 **2.6 ms**；改成一条 `setAttribute('style', …)` 而不是两次 `style.setProperty` 之后降到 **0.4–1.0 ms**（近两次复跑）。两次 `setProperty` 各自要解析一遍自定义属性并标记行内样式失效，合成一条声明串只走一次这条路径。

### 字号实测（真实浏览器）

`min(--ct-scale, --ct-cap)` 到底落在多少 px，只有真实浏览器算得出来 —— jsdom 没有布局引擎，也算不出层叠结果。`bench.html` 会挂一个探针把 `getComputedStyle().fontSize` 读回来，三轮完全一致：

| 元素     | 原文    | 译文          | 若没有封顶会是        |
| ------ | ----- | ----------- | -------------- |
| `<p>`  | 16 px | **12.8 px** | 12.8 px（未触发上限） |
| `<h2>` | 24 px | **16 px**   | 19.2 px        |
| `<h1>` | 32 px | **16 px**   | 25.6 px        |

页面基准字号 16 px，比例默认 80%。这张表就是「字体缩小了、而且标题不放大译文」的直接证据：`<h1>` 下若只写比例，译文会是 25.6 px，整页视觉重量直接翻倍。

探针的字号比例从 `CT.DEFAULT_SETTINGS.fontSizeScale` 读取，所以默认值再调时这张表会跟着变，不会停在旧数字上。

### 结构不变量怎么测的

第一版断言只数「顶层容器的直接子元素」，结果 `sibling` 也被判成通过 —— 因为合成页里每个单元都嵌在 `<article><section>` 深处，顶层容器始终只有那几十个 `<article>`，兄弟插入造成的错位根本反映不到顶层。**断言没有牙齿，等于没测。**

改成两条：

1. **原文元素的 `previousElementSibling` 是否仍是渲染前那一个** —— 它一变，说明译文插进了兄弟位置，相邻兄弟选择器与 `:nth-child` 就全错位了。
2. **忽略 `.ct-trans` 之后的整棵子树形状是否一致** —— 保证我们除了自己的译文块之外，没有添加、包裹或挪动任何页面元素。

改完之后 `sibling` 立刻报出 1475 处破坏（`inside` 为 0），说明这两条断言是真的在测东西。

### 关键改动

1. **单次扫描的字符分类器**（`detector.js`）。原本对每个待判定文本跑 10 次全局正则、每次分配一个匹配数组；改为按 UTF-16 码元单遍分类，扫描次数 10 → 1，零数组分配。
2. **中文目标下跳过拉丁语种打分**（`detector.js`）。判定「要不要翻」时不需要知道拉丁文本是英法德西中的哪一种，只需要知道它「不是中文」——整轮分词与停用词打分因此可以略过。这一步经 5156 条语料 × 4 种目标语言验证为严格等价。
3. **BFS 采集循环**（`renderer.js`）：子节点单遍遍历同时完成判定与入队、跳过判定结果缓存（同一元素不再判两遍）、无元素子节点的内联节点不再入队。采集分层实测：纯遍历 6.8 ms / 加抽取 13.8 ms / 完整 21.2 ms。
4. **不再依赖 `innerText`**（`renderer.js`）。`innerText` 要求布局是最新的，会在读写交织时触发强制同步布局。改为无布局依赖的文本遍历（含两条快路径，绝大多数元素直接走 `textContent`）。
5. **变更范围精确映射**（`content.js`）。原文变更只重扫「最近一个已登记的翻译单元」，而不是靠一个布尔标志把几十个变更目标坍缩成一次整页重扫。**同时修掉一个漏翻缺陷**：改动已翻译段落内部行内子节点（`<p>正文 <a>链接</a></p>`）的文字时，旧实现把重扫范围定为 `<a>`，而内联元素不产出单元，导致该段译文永久停在旧内容上。
6. **后台批次内去重**（`service-worker.js`）。真实页面重复文本占比很高，先去重再查缓存与请求。6 条含 3 条重复的输入只发 3 次请求。
7. **引擎解析结果透传 + 可用性记忆**（`providers.js`）。旧实现每批都重新解析引擎，一个 12 批的任务会查询 12 次内置模型可用性；现在该查询与批次数量解耦（60 秒记忆，语言包下载后主动失效）。
8. **`extractText` 快路径**（`renderer.js`）。译文块成了单元自己的元素子节点之后，`textContent` 快路径会因为「自身译文带 `translate="no"`」而退化成 TreeWalker，而「已译完的页面被重扫」恰恰是最热的路径。补了一条按注册表记录、直接从 `textContent` 末尾扣除自身译文的快路径（该轮实测已译状态重扫 23.8 → 20.7 ms）。
9. **插入点改为按 computed `display` 分流**（`renderer.js`，v1.3.0）。插入位置经历了「兄弟节点 → 单元内部末尾 → 按宿主类型分流」三步。前两步各自在一半场景上是错的（见第六节）。现在读一次 `getComputedStyle(el).display`，按五条分支决定插到哪、以什么形态插：内联级宿主出内联译文、横向弹性容器挂到容器之后、可换行的弹性容器留在内部并独占整行、绝对定位元素与纵向弹性/网格容器内部追加。决策**全部在采集阶段算完**并缓存在 `WeakMap`，渲染阶段一次读都不做，因此稳定态边际成本约 0.4 ms。
10. **字形与视觉规范**（`content.css` + `constants.js`，v1.3.0）。字号从「相对父元素的 95%」收窄到「相对原文的比例，并以页面基准字号封顶」，默认比例 0.95 → 0.85 → **0.80**；`.ct-trans` 拆成「结构层 + 修饰层」，基类不含任何颜色、边框、内边距与 `::before`，装饰下沉到 `ct-s-plain`（默认，零装饰）与 `ct-s-accent`。动机是：装饰本身就是对页面外观的改动，且逐段重复几百次。


1. **噪声文本闸门**（`detector.js`，v1.3.0）。新增 `looksLikeMarkup` / `looksLikeDataBlob` 两道判断，插在语言判定**之前**（噪声文本通常很长，先跑语种判定纯属浪费）。这是**有意的行为变更**，不是重构，因此在等价性测试里被精确隔离成三类统计（见第十节）。

### 布局保真：五条可执行的判据

「不改变原页面布局」如果只是一个形容词，就没法验收。它在 `bench-layout.html` 里被拆成五条能数出数字的判据：

| 判据               | 定义                                                                          | 抓住什么                      |
| ---------------- | --------------------------------------------------------------------------- | ------------------------- |
| **S1 结构不变**      | 忽略译文节点后，元素序列、标签、父子关系完全一致                                                    | 兄弟插入、包裹、挪动元素              |
| **S2 无宽度被挤压**    | 非译文元素的宽度不许变小（>0.5px）                                                        | 横向弹性容器被塞入新项后重新分配宽度        |
| **S3 内联宿主高度不变**  | `display` 属于 `inline` 系列的元素高度不许变（>0.5px）                                    | 行盒被块级译文打断（pill 被撑成两截）     |
| **S4 译文自身未被压扁**  | 块级译文的宽度不得小于宿主宽度的 60%                                                        | 译文被当弹性项压缩成一根竖条            |
| **S5 译文不落进裁切容器** | 没有译文的祖先链上存在 `overflow:hidden/clip` + `line-clamp`/`max-height`；零高度折叠区里一段都不翻 | 「翻了但看不见」与「翻了但搅乱站点自己的展开全文」 |

五条判据**明确排除了**「文档整体向下推移」与「承载译文的元素自身变高」——「原文下方双语」无法避免这两项，它们作为参考值单独报告（`hAll` / `hForeign`）。这一步很关键：不分开统计，「允许的变化」会把「真正的破坏」淹没掉 —— 第一版判据就是栽在这里。

在 39 个夹具（13 类宿主 × 3 次）/ 210 个非译文元素上，四种跑法同进程各跑一遍：

| 方式             | 宽度被挤压 | 内联宿主高度变 | 译文被挤扁  | 落进裁切容器 | 最窄译文      | 判定       |
| -------------- | ----- | ------- | ------ | ------ | --------- | -------- |
| **`auto`（默认）** | 0     | 0       | 0      | 0      | 93 px     | **PASS** |
| `inside`       | 0     | **9**   | **3**  | 0      | **40 px** | FAIL     |
| `sibling`      | **9** | 0       | **18** | 0      | 93 px     | FAIL     |

裁切专项（三组夹具 × 3 份，共 6 条译文需要被「救」出来）：

| 指标                | 实测    | 含义                                        |
| ----------------- | ----- | ----------------------------------------- |
| `rescuedFromClip` | **6** | 6 条译文原本会落进 `line-clamp` / `max-height` 容器 |
| `clippedTrans`    | **0** | 修完之后没有任何一条留在裁切子树里                         |
| `collapsedTrans`  | **0** | 零高度折叠区（`max-height:0`）里一段都没翻              |
| `afterPlacements` | **9** | 3 条横向弹性容器 + 6 条裁切容器走了「挂到容器之后」             |

S5 是有牙齿的：在修那个写反的守卫之前，`clippedTrans` 是 **6**、`rescuedFromClip` 是 **0** ——  
也就是这个分支一次都没生效过。改动前后 `wShrunk / xMoved / hInline / squeezed` 四项逐组完全一致，  
证明修的是「该生效却没生效」，不是「顺手改了别的行为」。

`inside` 那三处不是构造出来的：`chips`（`display:flex; flex-wrap:nowrap` 的标签行，容器自身就是翻译单元）里，译文块被当成新的弹性项，只剩 **40 px** 宽 —— 一屏在窄列里被竖向拉成长条，正是「整页看起来被压变形」的来源。`auto` 把它改成挂在标签行之后（不可换行时）或独占新行（可换行时），这个数字归零。

**这套断言有牙齿**：把它切回 `inside` 或 `sibling`，对应判据立刻报红。没有这一步，就不知道测试是不是恒真。判据的阈值也不是拍脑袋定的 —— S4 最初定 90%，会把表格单元格的正常内边距误报成「被压扁」（9 处），降到 60% 之后 `auto` 归零，而 `inside` 在 `chips` 上的 40 px 依然抓得住。

### 控件性能预算与布局中立性

页内开关是新增的常驻元素，它自己也要过一遍「零副作用」的账。  
`bench-toggle.html` 在真实 Chrome 里量三件事（夹具：600 段落 / 660 元素 / 正文高 38617 px，  
另加两个站点自有的 fixed 浮层）：

| 指标              | 预算     | 实测（20 / 60 次）                              | 判定   |
| --------------- | ------ | ------------------------------------------ | ---- |
| 挂载成本 `mount()`  | ≤ 5 ms | med **0.4 ms** / max 3.9 ms / 冷启动一次 0.7 ms | PASS |
| 状态刷新 `update()` | ≤ 1 ms | med **0 ms** / max 0.1 ms                  | PASS |

布局中立性（挂载前后的差值，全部必须为 0）：

| 量             | 差值       | 为什么                                            |
| ------------- | -------- | ---------------------------------------------- |
| 正文区高度         | **0 px** | 宿主是 `position: fixed`，不参与父容器排版                 |
| 正文区元素数        | **0**    | 控件挂在 `body` 下，不进正文容器                           |
| 文档总高度         | **0 px** | 不占文档流，不产生滚动条                                   |
| 横向滚动宽度        | **0 px** | 不撑宽页面                                          |
| `body` 直接子元素数 | +1       | **预期内**：宿主是 `body` 的一个子节点。它是 fixed，所以不影响上面任何一项 |

同一次基准还把结构约束钉住：宿主 `position` 为 `fixed`、`z-index` 为 2147483600、  
不在正文容器内、带 `data-ct-skip` 与 `translate="no"`、有 Shadow Root；  
主控件是原生 `<button>`、有 `aria-pressed` 与可访问名称。

> 为什么这些判据必须真机跑：**jsdom 里「挂载后高度没变」是恒真的**>   
> （`getBoundingClientRect` 一律返回 0），恒真的断言等于没断言。

注：控件挂到 `body` 下，而布局基准的遍历起点是 `#stage` —— 因此控件**不会进译文快照**，  
S1「结构不变」不会把它误判成「页面结构变了」。若今后把遍历起点改成 `body`，  
必须同步把 `ct-toggle` 登记进基准页的 `isOwn()`，否则会自报一个结构破坏。

### 为什么读 computed style 不会拖慢采集

`auto` 模式要为每个单元读一次 `getComputedStyle(el).display`。**跨轮次比对会得出错误结论**：`auto` 第一次是 3.7 ~ 4.7 ms，`inside` 是 0.8 ~ 1.3 ms，看起来慢了 3 倍多；但把 `auto` 在同一进程里再跑一遍是 **0.7 ~ 1.7 ms** —— 那约 3.0 ms 是整页**一次性**的样式重算，不是每个元素的边际成本。

| 采集阶段（39 夹具）                   | 冷启动（两次复跑）        | 稳定态（两次复跑）        |
| ----------------------------- | ---------------- | ---------------- |
| `auto`                        | 4.7 / 3.7 ms     | **1.7 / 0.7 ms** |
| `inside`（完全不读 computed style） | 1.3 / 0.8 ms     | 1.3 / 0.8 ms     |
| **净成本**                       | **≈ 3.0 ms 一次性** | **≈ 0 ms（噪声内）**  |

绝对值两次有波动，但「冷 − 温」这个差值两次都恰好是 **3.0 ms** —— 波动来自环境，不来自改动。

边际成本基本为零，因为：① 结果缓存在 `WeakMap`，跨轮次复用（已译状态重扫、变更后重扫都直接命中）；② 读取**全部集中在采集阶段**（纯读，不会因为自己的写入使样式失效），整轮最多触发一次重算。若挪到渲染阶段边写边读，就退化成强制重排。

> **测不准的地方要如实说**：2500 块页面上 `collect_cold` 单次运行内的抖动可以到 **23 → 66 ms**，比本轮改动引入的差异还大。所以这里不报「提速 / 变慢」的单次数字，只报两次独立复跑的区间：首屏采集 23.4 / 23.1 ms、已译状态重扫 22.1 / 21.1 ms、变更后整页重扫 19.6 / 20.1 ms。对照上一轮优化结束时的 21.9 / 23.8 / 20.6 ms，**在噪声带内，没有回退**；同机 `structure`（`inside` 0 / `sibling` 1475）与 `restoreClean: true` 两次完全一致。原始数据存于 `tools/bench-results/`。

```
打印可照做的指引并以退出码 1 结束     ← 而不是吐一段 MODULE_NOT_FOUND 堆栈
```

所以三种用法都可以：

```bash

```

- **`test-detector-equiv.mjs`**：优化涉及改写热路径分类器，因此用 19.5 万个码点逐点比对 + 5188 条语料 × 4 种目标语言。**这个测试抓到过两处真实转录错误**（漏掉 CJK 兼容表意区 `U+F900–U+FAFF`、星号平面边界多包 1504 个码点）。

  新增的噪声闸门是**有意的语义变更**，不能用「等价」两个字糊过去，所以这里把它精确地隔离出来：
  ```
  未经噪声闸门的差异：      0 条（必须为 0）
  被噪声闸门拦下（预期）：  805 条（只允许「要翻 → 不翻」这一个方向）
  反向差异（不翻 → 要翻）：  0 条（必须为 0）
  ```
  也就是说：**除了这道闸门，新旧判定链逐条相等**。闸门本身该拦什么、不该误伤什么，由 `selftest.mjs` 的正反样本单独断言。

### 已知偏差（如实列出，不打算改）

1. **设置页 7 张卡片视觉等权重**，弹窗 3 个统计格同理（条款 2）。     
   保留理由：卡片顺序已经承担重要性     
   （翻译引擎 → 翻译行为 → 页内开关 → 译文准确性 → 缓存 → 生效范围 → 快捷键），     
   卡内标题有 20 → 15 → 13 px 的字号层级，本轮又叠了一层 `<details>` 分组标题。     
   再叠一层「主卡更大」，会让设置页头重脚轻，收益小于代价 ——     
   这里选择**用排序、分组与字号表达层级，而不是用面积**。
2. **两个产品界面的字号未 token 化**（间距与圆角已全覆盖）。     
   12.5px 用于 `code`、状态胶囊这类次级文本，与 13px 在正文旁的可读性差异是稳定的；     
   强行归到任一侧都会让某一类文本偏离原本观感。文档层没有这个包袱，所以那里连字号一起收敛了。
3. **设置页卡片默认展开**（第三组除外），API Key 与「显示方式」同级（条款 4 渐进披露）。     
   这是产品侧最该改的一项，但改了会牵动信息架构，不宜随 UI 修复一起做。     
   **门槛写死：卡片达到 7 张时必须同步引入分组折叠** —— 那时排序已经表达不了层级。     
   这条规则不需要靠记性，数一数 `options/options.html` 里的 `<section class="card">` 就知道。     
   **当前状态**：卡片已到 **7 张**（新增「译文准确性」），**已按上面这条门槛引入分组折叠** ——     
   `options/options.html` 用三个 `<details class="group">` 把 7 张卡片分成：
   | 分组    | 卡片（`<h2>` 原文）      | 默认     |
   | ----- | ------------------ | ------ |
   | 翻译与显示 | 翻译引擎 / 翻译行为 / 页内开关 | 展开     |
   | 译文质量  | 译文准确性 / 缓存         | 展开     |
   | 范围与进阶 | 生效范围 / 快捷键         | **收起** |
   门槛的作用就是在这里生效的：7 张卡片平铺时，「靠排序表达优先级」已经撑不住，     
   分组标题必须站出来承担第一层层级，最后一组还要靠默认收起做渐进披露。     
   **验收方式：卡片数与分组数要一起看** —— 单看卡片数分不清「7 张已分组」和「7 张没分组」，     
   原来的判据在「7 张但已分组」时会给不出结论（见「验证 ⑤」）。
4. **页内开关刻意不接 `--sp-*` / `--r-*` 刻度**（条款 8）。     
   它运行在别人的页面上，整块 UI 关在 Shadow DOM 里，样式必须自带全套字面值 ——     
   依赖任何外部 CSS 变量，都会在该变量未定义时让控件直接塌掉。     
   这也是 `check-design-tokens.py` 的扫描范围**刻意不含** `content/toggle.js` 的原因：     
   那里的裸像素是设计决定，不是漏改。代价是改开关的间距要同时看两套刻度，容易走偏。
5. **开关的进度文案极长时会撑宽控件**（条款 15）。     
   进度写法是 `已译段数 / 总数`，超过四位数（如 `9999 / 12000`）时按钮会比默认宽。     
   不做省略号的理由：那个数字恰恰是用户此刻唯一需要看的信息，截断它等于把这个控件最有用的一态变瞎。     
   上限天然存在 —— 单页翻译单元默认上限 4000（`maxUnitsPerPage`）。

```bash
# ① 产品界面里不应再出现写死的版本号（页脚已改为现读 manifest）
#    末尾 -v '<code>' 是必须的：设置页正文里有「<code>v1.2.3</code> 被翻成 v1.2.3 版」
#    这类反例说明，那是**文案内容**，不是页脚版本号。
grep -rn 'v[0-9]\+\.[0-9]\+\.[0-9]\+' popup/ options/ | grep -v '<code>' \
  && echo "✗ 有写死版本号" || echo "✔ 无"

# ② 设计说明文档的「自称版本」必须等于 manifest 的版本。
#    判据只能扫**自称位置**（title / meta「版本」/ 页脚），不能扫全文档 ——
#    正文里的 v1.5.0 是在讲历史（「v1.5.0 新增的 144 项」「以下为 v1.5.0 追加」），
#    属正常引用。全文档扫会把「引用旧版本说明历史」判成违规，等于判据写错了位置。
grep -o '双语助手 v[0-9]\+\.[0-9]\+\.[0-9]\+' docs/布局保全设计说明.html      # 应为 v1.6.0（title + 页脚，2 处）
grep -o '版本 <b>[0-9]\+\.[0-9]\+\.[0-9]\+</b>' docs/布局保全设计说明.html    # 应为 1.6.0（meta 行，1 处）
# 一把梭：三处自称位置全都不含当前版本号即为异常（期望计数 3）
grep -c '<title>布局保全设计说明 · 双语助手 v1\.6\.0</title>\|版本 <b>1\.6\.0</b>\|双语助手 v1\.6\.0 · 布局保全设计说明' docs/布局保全设计说明.html

# ③ 带 for 的合法 label 数（改标签时不能误伤这些）
#    由 10 降到 9 —— sourceLang / targetLang 改成了 aria-label，原因见第二轮修复表下的注释。
grep -c '<label class="row__k" for=' options/options.html        # 应为 9

# ④ manifest 与 package 版本一致
grep -m1 '"version"' manifest.json package.json

# ⑤ 设置页结构：卡片数与分组数**一起看**（见「已知偏差 3」）
#    只数卡片数会在「7 张但已分组」和「7 张没分组」两种情况下给出同一个数，
#    所以原来的「数一数就知道」这个判据本身要改成两条。
grep -c '<section class="card">' options/options.html            # 当前 7
grep -c '<details class="group"' options/options.html            # 应为 3

# ⑥ 注入清单必须三处一致：manifest 的 content_scripts、
#    service-worker 的 CONTENT_FILES、以及测试里的加载列表。
#    漏改补注入那条链的症状是「装完没反应」，排查成本远高于维护一个数组。
grep -A8 '"js": \[' manifest.json | grep -o '[a-z/-]*\.js'
grep -A8 'const CONTENT_FILES = \[' background/service-worker.js | grep -o "'[a-z/-]*\.js'"
```

>
> - `docs/产品与界面复核报告.html` 是**历史快照**：它里面的 `v1.0.0` / `v1.3.0` / `v1.4.0`>

> - `docs/布局保全设计说明.html` 是**活文档**：自称版本（title / meta / 页脚）必须跟着版本走，>

>   同理 ① 要 `-v '<code>'`：设置页正文里有 `v1.2.3` 这样的**示例文本**。

## 十二、已知限制

这些是**有意为之的取舍**，不是待修的 bug：

| 限制                                | 说明                                                                                                                                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **默认不自动翻译**                       | 打开页面后等用户手动触发（页内开关 / 弹窗「立即翻译」/ 右键菜单 / 快捷键）。站点记忆优先于此默认：在 A 站手动开过一次，A 站仍会自动启动。想恢复旧行为在弹窗或设置页打开「自动翻译」。**老安装升级后由一次性迁移强制收为关闭**——旧版本把默认值 `true` 持久化进了存储，不迁移则新默认永远不生效；迁移只跑一次，之后用户手动打开会被尊重     |
| **iframe 内的正文不翻译**                | 默认 `all_frames: false`。若需要，把 `manifest.json` 里改成 `true` 即可，但会造成同一页面重复注入                                                                                                              |
| **Shadow DOM 内的内容不翻译**            | 需要针对每个站点的 shadow root 单独处理，通用成本过高                                                                                                                                                    |
| **输入框、下拉框的文本不翻译**                 | 翻译可编辑区域会破坏用户正在输入的内容；`placeholder` 同理                                                                                                                                                 |
| **图片里的文字不翻译**                     | 需要 OCR，超出本扩展范围                                                                                                                                                                       |
| **「仅显示译文」会丢行内链接**                 | 该模式用整体替换实现；需要保留链接请用「原文下方双语」                                                                                                                                                          |
| **实时变动的内容会被拉黑**                   | 时钟、浏览量、倒计时这类每秒变动的元素，累计变动超过阈值后会被永久跳过，避免持续烧接口额度                                                                                                                                        |
| **短文本可能被漏掉**                      | 少于设置里「最少文本长度」的片段不翻译，避免产生大量碎片译文                                                                                                                                                       |
| **场景识别只覆盖已定义的场景**                 | 目前只有「招聘与求职」一个场景；URL / 标题强信号或正文 ≥4 个不同关键词才判定，宁可漏识别不误识别。未识别页面的多义词（Apply / Executive 等）仍按引擎默认取义                                                                                         |
| **未知品牌名仍可能被意译**                   | 只有内置清单里的品牌（GiveWell / Sticker Mule / Harper 等）保证保持原样；任意品牌自动识别误伤率不可控，未做。遇到新品牌在术语表里加一行 `品牌名 =` 即可                                                                                      |
| **只识别元素自身或内联样式上的隐藏**              | 采集文本不再使用 `innerText`（它会强制同步布局）。代价是无法感知「由外部样式表造成的 `display:none`」。已显式覆盖 `[hidden]`、内联 `display:none`、`[translate=no]`、`.notranslate`、代码与表单标签 —— 真正会遇到的绝大多数情形都在内。这条取舍是为了消除注入脚本对页面布局的依赖 |
| **原文段落自身会变高**                     | 「原文下方双语」要在原文下方放一段中文，这个高度无法凭空消失。默认分流里，「内部追加」把它记在原文单元头上（更符合语义，也不破坏容器结构），「插到容器之后」则记在父容器上。基准里这两项作为 `hAll` / `hForeign` 单独报告，不混进判据                                                        |
| **段落带背景色时，背景会把译文一起包住**            | 这是「内部追加」的代价。若某站点上观感不对，把设置页的「译文插入方式」切成「插到原文之后」即可                                                                                                                                      |
| **不可换行的横向弹性容器，译文只能挂到容器之后**        | `flex-wrap: nowrap` 时追加进去必然挤占原有子项宽度，所以分流会选择「插到容器之后」。代价是译文与原文隔了一个容器，但**至少原有子项一个都不动** —— 这是两个方案里代价更小的那个。可换行的容器则留在内部并独占整行                                                               |
| **译文默认区分度靠字号与透明度，不靠装饰**           | 默认「素净」样式不加「译」标记、不加色条，只把字号调到 80%、透明度降到 0.82、颜色取 `inherit`。需要一眼区分时在设置页切成「标注」（加一条左侧竖线 + 淡色「译」标记）—— 代价是这两样装饰本身就是对页面外观的改动                                                                 |
| **`getComputedStyle` 会付一次整页样式重算** | 首次进入页面时约 3 ms（2500 块页面上测得），小页面基本感知不到。之后靠 `WeakMap` 缓存，稳定态边际成本约 0.4 ms                                                                                                                |

## 十三、调试

- **看注入脚本的日志**：在页面按 F12，Console 里过滤 `双语助手`
- **看后台日志**：`chrome://extensions/` → 本扩展 → 点 **Service Worker** 打开它的控制台
- **译文没出现**：
  1. 看页面右下角有没有进度徽标（没有 = 脚本没注入或页面已判定为中文）
  2. 弹窗里「识别语言」是否显示为中文——若显示成中文，说明整页被判定为无需翻译
  3. 引擎配置是否完整，用设置页的「测试当前引擎」确认
  4. Google 接口返回 429 说明被限流，把「并发请求」调低到 2 再试
- **想临时停掉某一段的翻译**：给那个元素加 `translate="no"` 或 `class="notranslate"`
- **想永久跳过某个区域**：在设置页「跳过的区域」里加 CSS 选择器

## 十四、隐私

- 译文缓存只存在本机 `chrome.storage.local`，不上传任何服务器
- 选择 **Chrome 内置模型** 时，页面文本完全不出本机
- 选择其他引擎时，**只有待翻译的文本片段**会发往该引擎，页面 URL、Cookie、DOM 结构都不会被发送
- 扩展不收集任何统计数据
