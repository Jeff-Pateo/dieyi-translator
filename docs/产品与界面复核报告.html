对两个问题的直接回答

问题一：是否咨询了产品、业务 skill？

上一轮没有，这是事实。当时本机未安装任何产品类或业务类 skill， 可用清单里与本任务沾边的只有 ardot-ui-design（UI 规范）与 chrome-extension-mv3-build（架构）， 两者都不是产品/业务视角。所以上一轮只做了 UI 规范核对，并把这件事如实说成了「只做了 UI 核对」， 没有把 UI 核对包装成产品评审。

本轮由产品战略团队补做：按其手册第 3 节（竞品简报）、第 4 节（用户研究综合）、第 5 节（指标评审） 三条工作流并行复核，产出本文第 4、5、6 节。UI 那一节也重做过一遍，并且找出了上一轮漏掉的 3 处缺陷。

问题二：设计是否满足 UI skill？

依据 ardot-ui-design/references/guidelines-web-app.md 的 16 条结构、认知与产品品质法则逐条核对： 14 条硬性满足，2 条为有理由的已知偏差（第 2 条「主导区域」、第 8 条的「字号未 token 化」部分）， 两条偏差都在第 2 节写明理由与代价，不打算改。

本轮新发现 3 处真实缺陷（不是风格偏好，是可验证的状态失真与语义错误），全部已修： 设置页页脚写死 v1.0.0 而 manifest 已是 1.4.0； 8 处 <label> 没有关联任何控件；设计说明文档自称 v1.3.0。

一句话总结

UI 层的问题已经收敛到一个可复现的检查脚本能守住的程度； 产品层的真问题不在界面，而在功能缺口 —— 没有划词翻译、不支持 PDF 与多格式。 这两项是这一品类的入场券，不是加分项。详见第 4 节的行动建议。

偏差 1 — 主导区域（第 2 条）

弹窗 3 个统计格、设置页 5 张卡片视觉等权重。保留理由：卡片顺序已经承担了重要性 （引擎 → 行为 → 范围 → 缓存 → 快捷键），卡内标题存在 20 → 15 → 13 px 的字号层级。 再叠一层「主卡更大」，会让设置页头重脚轻，收益小于代价 —— 这里选择用排序和字号表达层级，而不是用面积。

偏差 2 — 字号未 token 化（第 8 条）

两个产品界面的间距与圆角已全部 token 化，字号没有。12.5px 用于 code 与状态胶囊这类次级文本， 与 13px 在正文旁的可读性差异是稳定的；强行归到任一侧都会让某一类文本偏离原本观感。 文档层没有这个包袱，所以那里连字号一起收敛到 --fs-1..--fs-8 八档。

定位判断：差异化站得住，但护城河窄

站得住的理由：「排版会不会被弄乱」是这一品类最集中、最具体、最容易被用户当场感知的公开抱怨。

  • 彩云小译：复杂网页排版偶尔错位，且会把原网页背景色改成纯白，被评测直接点评为「破坏了原本的阅读排版」
  • Google 翻译：翻译后原文消失，根本没有双语对照
  • DeepL 扩展：仅部分支持双语对照

也就是说，竞品在这一维度上是有伤而不是无感。把「不改变原页面布局」从形容词变成三条可数出数字的判据 （结构不变 / 宽度不许变小 / 内联宿主高度不许变 / 译文自身不被压扁）， 既是工程约束，也正好是可以拿去和竞品做同题实测的对比口径。

护城河窄的理由（必须说清楚）：

  1. 布局保真是工程质量，不是专利。沉浸式翻译已被第三方评为「布局友好、UI 侵入性低」，说明这条赛道上对手不缺能力，只是优先级不同。
  2. 能被复制就撑不起长期差异化。真正难复制的是另外两个组合：①「Chrome 内置本地模型 + 可自建网关」构成的隐私闭环；②「扩展不收集任何统计数据」这个可以写进隐私政策的承诺。前者是能力壁垒，后者是信任壁垒 —— 但这两条用户感知弱，不会让人当场换工具。
  3. 缺口恰恰在入场券上。没有划词翻译、只支持网页，而这两项是竞品普遍具备的基础能力。用户不会因为「布局更稳」去容忍「不能划词」。

最关键的 5 条待验证假设

#假设（可证伪）验证方法若被推翻意味着
H1「不改变原页面布局」是用户选择翻译扩展时的首要或次首要决策因素对比访谈 + 可用性测试，n ≥ 8整个差异化主张失去立足点，需要重新找定位
H2用户能感知到「译文独占整行」与「译文被挤成竖条」的差别，并偏好前者A/B 可用性测试，让用户在两版渲染结果中选布局判据赢了指标但赢不了体感，投入产出比要重估
H380% 字号是「明显小一号但仍好读」的最优点字号阶梯测试（75 / 80 / 85 / 90%），n ≥ 30默认值需回调；这是当前唯一没有用户背书的默认值
H4默认「素净」样式优于「标注」样式首次使用偏好测试，n ≥ 50默认值应改为「标注」，或改为按站点类型自动选择
H5缺少划词翻译会让泛浏览型用户直接放弃本产品流失访谈 + 竞品切换原因回收若不成立，可继续把划词排在 PDF 之后；若成立，应提前其优先级

证据强度：必须如实说

上述所有假设的当前证据强度都是「弱」或「无」，唯一可引用的是第 4 节那批竞品公开抱怨 —— 那是别人用户对别人产品的抱怨，只能作为假设的来源，不能当作对本产品的验证。 本产品至今没有任何一手用户证据。这是当前最大的信息缺口，且它比任何 UI 缺陷都更值得优先解决。

06指标框架（隐私约束下）

先摆约束：本产品在 README 中明确承诺不收集任何统计数据。 因此每个指标的第一道关卡不是「有没有用」，而是「本机能不能算出来、不出网」。 做不到的一律标注「需要隐私权衡」，不默认偷偷埋点。

北极星指标

本页译文覆盖率 = 本页已译单元数 ÷ 本页候选翻译单元数

选它的理由：这是唯一一个直接衡量「用户有没有真的拿到对照阅读价值」的指标 —— 装上了但没翻出东西，覆盖率就是 0。它比「安装量」和「日均使用次数」都更贴近产品核心价值。

关键优势：两个字段运行时已经在报（translated 与 units）， 不需要新增任何采集代码，也不需要上传任何东西 —— 零隐私代价。

AARRR 骨架与可得性

层级指标可得性说明
获取商店安装量、曝光转化本轮无法获得需商店后台数据，与扩展运行时无关
激活首装后首次成功翻译的到达率与耗时本机可得可从「首个译文落地时刻 − 脚本注入时刻」算出
留存回访用户 / 周活需隐私权衡替代方案：本机累计计数 + 用户主动导出，绝不自动上报
收入—不适用当前无商业化；自备 Key 的成本由用户自有账户承担
推荐—本轮无法获得无分享链路，也没有可归因渠道

守门指标：防止「北极星涨了但产品变差了」

#守门指标阈值 / 报警条件为什么需要它
G1布局保真四判据（结构不变 / 宽度不许变小 / 内联宿主高度不许变 / 译文不被压扁）任一非 0 即视为回归覆盖率可以靠「更激进地插入译文」刷高，代价正是弄乱页面 —— 这条直接对冲
G22500 块页面的首屏采集耗时超过 25 ms（基线 20.0 ms，留 25% 余量）覆盖率可以靠「多翻一点」刷高，代价是页面卡顿
G3还原后的残留检查（restoreClean）必须为 true关闭扩展后页面必须回到原样，这是「不改动用户页面」承诺的底线
G4出网域名白名单出现白名单外的域名即 P0覆盖率可以靠「偷偷多发几个请求」刷高。白名单必须严格等于「所选引擎域名 + 自建网关」，这一条比任何指标都重要
G5接口失败率（429 / 5xx）超过 10% 自动降并发失败会让覆盖率虚低，同时把用户推向被限流的深渊

如果只允许先上 3 个（全部零隐私代价）

  1. 本页译文覆盖率 —— 数据已有（translated / units），直接算。
  2. 首个译文到达耗时 —— 需新增一个本机时间戳差值，改动量极小，但它决定了用户对「快不快」的第一印象。
  3. 布局保真四判据 —— 夹具版已经跑通（tools/bench-layout.sh），下一步是拿到真实站点上抽样巡检，把「合成页全绿」变成「真实世界也全绿」。

P0 获取一手用户证据（至少验证 H1、H2） 产品 / 用户 最高 当前所有产品判断都建立在「竞品的用户抱怨」和「我们的工程推测」之上。不补这一步，后面所有优先级排序都是在猜

P4 PDF / 多格式支持 功能缺口 中低 沉浸式翻译靠这一项拉开身位，但工程量显著，且与本产品「不改动原排版」的主张关联较弱
P5 两个产品界面的字号 token 化 UI 一致性 低 见第 2 节偏差 2。收益是检查脚本能少一类例外，代价是可能需要重调次级文本观感
