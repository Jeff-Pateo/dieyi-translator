SECTION 01问题定义：把「不变形」变成可验证的判据

1.1 为什么形容词式的承诺不可接受

原始需求是「不能改变原页面布局」。这句话如果只写在文档里、不落成可执行的检查， 它就等价于没有约束 —— 因为任何一次改动都可以自称「没动布局」。 上一轮的做法就是把决策从「看起来差不多」换成四条可量化的判据； v1.6.0 又补了第五条 S5，专治「翻了却看不见」这一类不改变任何几何量的失败。

编号判据量化方式它抓的是什么
S1 结构不变 比对 tagName + 父子链 + previousElementSibling 的 tagName 父子关系、容器子项数、:nth-child、相邻兄弟选择器是否被破坏
S2 非译文元素宽度不许变小 getBoundingClientRect().width 逐元素前后比对 「被挤」这件事本身 —— 标签行里原有标签被平分掉宽度，就是这条报红
S3 内联宿主高度不许变 仅统计 display 属于 inline 系列的元素 行盒被打断 —— pill / 标签被块级译文撑成两截、定高宿主被撑破
S4 译文自身不被压扁 译文宽度 ÷ 宿主宽度 < 60% 即报红 译文被当作弹性项平分宽度后，在窄列里拉成一根竖条
S5 译文不落进裁切容器 祖先链（上溯 6 层）中是否存在 overflow:hidden|clip 且（有效的 -webkit-line-clamp 或 max-height > 0）；零高度折叠区单独统计 「翻了但看不见」 —— 站点的 line-clamp / max-height 容器会把插在里面的译文裁掉； 以及「翻了但搅乱站点自己的展开全文」
这一条与 S1–S4 有一个本质区别：它不靠几何量报红 —— 译文被裁掉之后，页面所有元素的宽高都不变，前四条判据全绿。所以必须单独设一条。

1.2 明确豁免的两项（如实报告，不混进判据）

「原文下方双语」这个产品形态决定了有两类变化是设计本身要求的， 不能用它去污染判据，但也不能藏着不说，因此单独上报：

指标含义为什么豁免
hAll 元素自身的绝对高度变化，含「因为下方多了一段文字而变高」 文档整体下移、承载译文的段落变高 —— 下方双语无法避免
hForeign 高度变化被归因到「子元素承载了译文」的祖先 由 plan.own 反向传播识别：高度变化的责任方是那个真正装了译文的元素，不是它的祖先
关键区分

S3 只数非译文的内联元素。承载译文的元素自己变高是允许的（hForeign）， 但旁边那些没被翻译的内联元素高度一变，就说明行盒真的被破坏了。二者必须分开统计， 否则「允许的变化」会把「真正的破坏」淹没掉 —— 这正是第一版判据没有牙齿的原因。

SECTION 02形变机制归因（五条）

截图里的「形变」不是一个 bug，是五条独立机制叠出来的同一类结果。 下面每一条都给出机制解释与可复现的量化证据（数据来自 tools/bench-layout.html）。

#机制为什么会这样量化证据
① 译文块被塞进横向弹性容器 容器是 display:flex + 行方向，追加一个子元素 = 新增一个弹性项。容器宽度固定时，浏览器只能把所有弹性项的宽度重新平分，原本的标签被分掉宽度，译文自己也被压成一根竖条 chips 夹具（flex / nowrap / width:420px）下，inside 模式的译文最窄只剩 40 px，判据 S4 报 3 处挤扁
② display:block 强规则落在内联级宿主上 宿主是 inline-block / inline-flex 这类内联级元素时，它的内部仍然是一个行盒。塞进块级译文会打断这个行盒，宿主被拆成上下两截、高度翻倍 pills 夹具下 inside 模式判据 S3 报 9 处内联宿主高度变化
③ 定高宿主内容溢出被撑破 标签式 UI 常给 pill 设 height 或 line-height，一旦内部多出一块块级内容，内容就溢出盒子边界，视觉上是「被撑开 / 露出背景」 同 ② 的 9 处 —— 溢出与高度变化是同一根因的两个观测面
④ HTML 源码 / JSON-LD 被当成正文翻译 有的页面把整段 HTML 源码或结构化数据渲染在 <pre> / 隐藏容器里。这些文本译文毫无意义，而且体积极大 —— 在窄列布局里会被拉成一根很长的竖条，看起来就像整页变形 加闸门前后 markup / jsonld 两类夹具的译文数从「有」变为 0（transInMarkup: 0、transInJsonld: 0）
⑤ 译文自身的装饰就是视觉改动 ::before 的「译」标记、左侧色条、内边距 —— 单看一处是小事，但它在整页每一段上重复几百次，累积起来已经构成对页面外观的实质修改 默认样式由「标注」改为素净：无边框、无标记、无内边距，只保留字号与透明度差异

SECTION 03插入点决策树

3.1 为什么不能只看标签

早先的两种全局策略，每种都恰好在一半场景上是错的：

  • 一律插成兄弟节点。代价全落在父容器上 —— 子项数翻倍、:nth-child 错位、 p + p 失效；在 display:flex 的行容器里，译文会变成一个新弹性项， 和原有子项平分宽度（机制 ①）。
  • 一律追加进单元内部。那么在横向弹性容器（译文变成弹性项）与内联级宿主（行盒被打断）上翻车（机制 ②）。

关键在于：光看标签判断不出来。<div> 既可能是普通块， 也可能是弹性行容器。只有 getComputedStyle(el).display 能区分。 所以决策的第一依据是「这个元素实际怎么排版」，而不是「它叫什么标签」。

为什么 wrap 的弹性容器宁可留在容器内，也不挂到外面

因为容器允许换行时，新项可以自己去新的一行，原有子项宽度完全不受影响 —— 此时留在容器内部反而更好：译文与原文的归属关系还在， 也不会让容器的 :nth-child 错位。这是「挂到外面」与「留在里面」两个方案里更优的那个。

3.4 安全锚点：最多上溯 4 层

需要挂到容器外面时，锚点不能随手选父节点 —— 父节点本身可能也是个弹性容器， 挂到它之后同样会变成新的弹性项。safeAnchor() 因此向上寻找第一个不处于 弹性 / 网格 / 表格行上下文的祖先，最多上溯 4 层。

为什么是 4 层而不是无限上溯：译文离原文越远，归属感越弱。 与其把译文扔到页面顶部一个「安全」的位置，不如就地退化 —— 用户至少还能看出这句译文对应哪段原文。

3.5 决策前移到采集阶段（这一条同时也是性能设计）

getComputedStyle 是只读的，但在边写边读的场景里它会退化成 强制同步布局：每次读取都强迫浏览器把刚写的样式重新算一遍。 渲染阶段正是在不停地写 DOM。

所以决策全部在采集阶段算完，把结果（plan）挂在单元对象上随之下传。 采集阶段是纯读，整轮最多触发一次样式重算。结果同时缓存进 WeakMap， 跨轮次复用 —— 同一元素反复采集也只读一次。 

// 采集阶段：纯读，算完就存；这是唯一一次样式重算
out.push({ el, text, hash, plan: placementFor(el, settings) });

// 渲染阶段：只按 plan 落地，一次读都不做
renderUnit(unit, text, style, wave[k].plan);
实测成本

在 39 类宿主夹具上同进程交替测量，两次独立复跑：auto 冷启动 4.7 / 3.7 ms、温态 1.7 / 0.7 ms；完全不读样式的 inside 1.3 / 0.8 ms。

两次都指向同一个结论：一次性成本约 3.0 ms，稳定态边际成本落在噪声内（≈0）。 详见 §7。

3.6 裁切容器：让译文根本不进入会被裁掉的子树（v1.6.0）

前四轮修的形变都有一个共同点 —— 几何量会变，所以 S1–S4 抓得住。 但用户报的这条不一样：「中文翻译后存在被隐藏内容无法显示更多」。 这里的失败是译文被站点自己的裁切容器吃掉：

  • 站点用 -webkit-line-clamp:3 做「摘要三行」，译文插进这个容器里，第 4 行起就看不见了；
  • 站点用 max-height:200px; overflow:hidden 做固定高度卡片，译文一插进去就被裁掉一截；
  • 更麻烦的是，这类容器往往带着站点自己的「展开全文」按钮。译文撑高了内容， 按钮的折叠逻辑按站点原有的高度阈值判断，于是「点展开」的行为跟着错乱 —— 我们改了别人页面的交互。

关键洞察：译文被裁掉之后，页面所有元素的宽高都不变。S1 结构没动、S2 宽度没挤、 S3 高度没变、S4 译文也不扁 —— 前四条判据全绿，但用户什么都看不到。这就是必须单独设 S5 的原因。

两条判据刻意分开

判据成立条件处理方式
clipsContent(el)
会被裁		 overflow-x|y 属于 hidden / clip，且满足其一：
· -webkit-line-clamp 是有效数值（≥1）
· max-height 解析为 > 0 		译文挂到容器之后（reason:'clipped'），不进它的子树

这两条为什么不能合并成一条「被裁切」

看上去 max-height:0 只是 clipsContent 的一个特例，合并起来更简单。 但合并之后，max-height:0 的折叠区会走进「挂到容器之后」那个分支 —— 于是页面上每一个收起的折叠块旁边，都会凭空多出一段译文。

零高度折叠区（典型的 <details> 未展开体、JS 折叠面板）里的内容是 用户主动选择不看的，译文不该替用户把它摊开。 所以判据必须分开：会被裁 → 挪出去；完全零高度 → 不翻。 这条在 selftest.mjs 里有专门的反向断言：夹具写明「max-height:0 不是 clipsContent」，注释里写着合并会造成的具体后果。

取最外层，不是最近一层

clipInfo(el) 沿祖先链最多上溯 6 层（CLIP_HOPS），返回最外层那个裁切容器。 嵌套裁切（外面 max-height、里面 line-clamp）很常见，如果只取最近一层， 译文被挪到内层容器之后，还是会被外层裁掉。

这个探测不进 WeakMap 缓存，与 layoutOf 不同。 原因是裁切状态会随站点自己的交互变化（点「展开全文」之后 max-height 就没了）， 缓存下来会让「展开之后再翻」拿到过期结论。上溯 6 层是纯 DOM 遍历，不触发样式重算，代价可接受。

一个曾经写反的守卫

分支写好了，基准跑出来却是 clippedTrans = 6、rescuedFromClip = 0 —— 这个分支一次都没生效过。原始守卫是： 

// ✗ 恒为 false：safeAnchor 一路向上走，返回的锚点必然是 el 的祖先，祖先当然 contains(el)
if (clipAnchor !== el && !clipAnchor.contains(el)) { return { kind: 'after', anchor: clipAnchor }; }

条件「锚点不包含自己」在一个上溯求锚点的函数里永远不成立， 于是每次都退化到 inside。修复不是把条件反过来（那会走进另一侧的恒真）， 而是把判据换成真正想问的那个问题：「这个位置插不插得进去」。 

function canInsertAfter(anchor, el) {
  // 锚点必须有元素父节点；父节点不能在收不下块级子元素的白名单里（tr / select…）；
  // 锚点不能是 el 自己的后代（否则等于把译文插回原文内部）
  return !!anchor.parentElement
      && !NO_BLOCK_CHILD[anchor.parentElement.tagName]
      && !el.contains(anchor);
}

修后 clippedTrans = 0、rescuedFromClip = 6。 更关键的是改动前后 wShrunk / xMoved / hInline / squeezed 四项逐组完全一致 —— 这证明修的是「该生效却没生效」的缺陷，而不是顺手改了别的行为。没有这组对照， 就分不清「新分支生效了」和「只是测试数字变了」。

为什么不用「给译文加个 class，让站点别裁它」这个更省事的做法

给 .ct-trans 加 -webkit-line-clamp:unset 之类，等于直接改站点自己的样式 —— 而且改的是容器，不是译文。容器上还挂着站点的折叠逻辑与「展开全文」按钮， 我们一动它，站点自己那套就跟着坏。把译文挪到容器之外，站的还是「不动别人页面」这条底线： 只往页面上增加自己的节点，不修改任何既有元素的样式与结构。

SECTION 04译文视觉规范（UI）

4.1 字号：两条规则相乘，而不是一条

译文大小 = min(相对原文的比例, 页面正文基准字号)。两条缺一不可。

  • 相对原文的比例（默认 80%，设置页可调、拖动即时生效）负责让正文段落里的译文「小一号」。
  • 页面基准字号封顶负责标题。百分比字号是相对父元素解析的： 译文插进 <h1> 之后，父元素就是那个 32px 的标题， 光写比例会让译文也变成 25.6px，整页视觉重量直接翻倍。

基准字号只读一次 body 的 computed font-size，并按 11–18px 钳制； 整页只读这一次，不随单元数增长。

宿主宿主字号比例（80%）封顶值译文最终说明
正文 <p> 16 px 12.8 px 16 px 12.8 px 比例生效，读起来明显小一号
标题 <h2> 24 px 19.2 px 16 px 16 px 被 cap 压住 —— 与正文基准同号，不会撑大视觉重量
大标题 <h1> 32 px 25.6 px 16 px 16 px 同上 —— 没有 cap 的话这里会是 25.6px

4.2 默认样式：素净（plain）

装饰本身就是「改变页面」。一个「译」字标记加一条色条， 在整页每一段上重复几百次，就已经不是「保持原样」了。

样式效果代价
素净 默认 不加边框、不加背景、不加「译」标记；字号调小、opacity:0.82、颜色取 inherit 几乎为零 —— 深色页、品牌色底、图片背景上都跟随页面，不会糊掉
标注 左侧 2px 竖线 + 淡色「译」标记，一眼区分原文与译文 这两样装饰本身就是对页面外观的改动，且逐段重复

4.3 结构层与修饰层分离

  background: transparent !important;

4.6 页内开关：可发现性与状态语义（v1.6.0）

页内开关（content/toggle.js）跑在别人的页面上，它的设计约束和弹窗/设置页不同： 用户不会「打开」它，只会撞见它。所以「好不好看」不重要， 「一眼看出它是干什么的、现在处于什么状态」才重要。用户反馈的「开关设计的并不合理， 而且不易察觉如何使用」正是这条没做到。

三处改动，对着三个具体症状：

症状原来的做法改法
不知道按钮是干什么的 文案是形容词「已译」—— 说的是状态，不是动作。用户看到一个状态词， 不知道该不该点，也不知道点了会发生什么 全部改成动词在前：翻译此页 / 显示原文。 形容词描述现状，动宾短语描述下一步 —— 后者才能回答「我该做什么」
找不到次要功能 「站内不再翻译」「打开设置」等收在悬停才浮现的工具区里。 触屏设备根本没有悬停态，鼠标用户也要先撞上才知道有东西 工具区改为常显，并且把内容收进一个 ⋯ 菜单（aria-haspopup + role="menuitem"，键盘可达）。常显的是入口，不是内容 —— 这样既不占地方，也不用猜
看不出会译成哪门语言 图标恒为「译」字。支持多语言互译之后这个图标彻底失去信息量 —— 同一个图标，可能是译成日文，也可能是译成英文 图标改为目标语言标记：CT.langMark('ja') === '日'、 'en' === 'EN'、繁体中文是「繁」。 图标本身成为状态的一部分，用户不必去设置页回想「我上次设的是哪门语言」

首次使用的一次性引导

控件再清楚，第一次见到它的人也不知道页面上多了这个东西。 所以首次注入时在开关旁显示一个引导气泡，说明「点击此处翻译本页」， 并在气泡上留一个关闭入口。点「知道了」、或发生任何操作之后， toggleGuideDone 落盘，永久不再出现。

为什么是「一次性」而不是「可关闭的常驻提示」

常驻提示会变成用户每天要手动关掉一次的东西，而它承载的信息只在第一次有用。 判断一次性的标准不是「重不重要」，而是「第二次看还值不值」。 落盘用的是设置里的布尔位而不是 sessionStorage —— 后者在每次新开标签页都会重置， 等于把「一次性」做成了「每天一次」。

三个浮层必须互斥

开关上有三个可展开的东西：⋯ 菜单、引导气泡、黑名单二次确认。 它们都由同一个小控件触发，位置重叠，各自还带点击外部关闭的行为。 如果同时打开，不但互相遮挡，点击外部该关谁、Esc 该按几层都会变得不可预测。

因此统一收进一个 closeOverlays(except)：打开任一层先关掉其余两层， 点控件外部或按 Esc 逐层收起。 关键细节是这条逻辑对 update() 这条直写通道同样生效 —— 后台推来的状态更新（比如黑名单判定结果）如果直接改 DOM，会绕过互斥逻辑， 所以 update() 里在检测到确认条状态变化时，同步关掉菜单与气泡。

这条为什么归在「布局保全」文档里

因为开关是唯一一个默认存在于别人页面上的我们自己的 UI。 它的浮层一旦失控，破坏的是宿主页面的观感与交互 —— 这与「不动别人页面」是同一个约束，只是从几何层换到了交互层。

SECTION 05判定闸门（业务）：噪声、语言口径、不可译片段

5.1 为什么「能翻就翻」是错的

原始的判定逻辑是纯技术性的：够长、不是邮箱、不是 URL、语种是外语 → 翻译。 但业务上有一类文本不该翻：机器可读的源数据。它有两重危害：

  1. 翻译无意义 —— 把 <div class="card"> 翻成中文，用户看到的是一串乱码般的产物。
  2. 体积极大 —— 一段 HTML 源码或 JSON-LD 动辄几百上千字符，插进窄列布局后会被拉成一根竖条， 视觉上就像整页变形（机制 ④）。

function isTranslatableText(text) {
  // …长度下限、邮箱、URL…
  if (looksLikeMarkup(text))  return { ok: false, reason: 'markup' };
  if (looksLikeDataBlob(text)) return { ok: false, reason: 'data-blob' };
  // …语言判定（最贵的一步）…
}

5.5 语言判定：单一数据源与简繁严格口径（v1.6.0）

原先目标语言只有「简体中文 / 繁体中文」两项，判据散落在三处： 设置页的 <select>、弹出面板的语言名映射、以及后台提示词里的语言名。 加一门语言要改三处，漏改一处的症状是静默的 —— 下拉里能选，提示词里却还是中文。

现在语言表下沉为单一数据源 CT.LANGS（41 种，每种带一个 mark 标记）： 

CT.SOURCE_LANGS = [{ id:'auto' }].concat(CT.LANGS);   // 源语言多一个「自动识别」
CT.TARGET_LANGS = CT.LANGS;                            // 目标语言是全集

CT.langLabel(id)   // "日本語"        —— 设置页下拉与 title
CT.langMark(id)    // "日"            —— 页内开关的图标
CT.langShort(id)   // "日" / "EN" / "繁" —— 弹窗统计格（88px 宽放不下全名）

后台的 LANG_PROMPT_NAME（41 条）与这份表同源， DeepL 的 DEEPL_TARGET_MAP 也补齐了 —— 遇到底层引擎不支持的语向， 现在是明确报错，而不是悄悄按中文处理。

简繁为什么必须按「不同语言」判

把 zh-Hans 和 zh-Hant 当成同一种语言，会让整页闸门失效 —— 页面是繁体、用户要简体，闸门判「已经是目标语言」直接不翻。反过来也成立。 所以 isSameLanguageStrict() 采用严格口径：简繁算两种语言。

但严格口径需要一个可靠的判据。scriptVariant() 的做法是投票， 依据是一张 CT.VARIANT_PAIRS（120 对成对锚点表）： 每对是同一个字在简繁两侧的写法（国/國、这/這、后/後…）。 这张表有四条入选约束，缺一条就会让投票偏向错误的一侧：

约束为什么必须
两侧等长不出现「一个简体对两个繁体」，否则同一次命中在两侧计的不是同一票
各自无重复同一个字在同一侧出现两次，会让那个字被计两票 —— 投票变成加权，而权重是笔误
两侧无交集最常见的坑：简繁同形的字（如「人」「中」）两侧都收，投出来的结果恒为平票
无同形废对后/後 之外的「看起来一样其实一样」的对要剔除，它们只有噪声，没有信号

整页闸门也从「源语言 === 目标语言」换成 needsPageTranslation(source, target, variant) —— 必须把检测出的 variant 一起传进来，否则简体页面配繁体目标会被误判为「无需翻译」。 控件状态（「无需翻译」四态之一）用的是同一条判据，不会出现「按钮说不用翻、闸门却放行」这种自相矛盾。

5.6 不可译片段掩码：让引擎不该改的东西改不了（v1.6.0）

用户报的「部分翻译不正确，请校准」里，有一类根源不在引擎的翻译质量，而在 我们把不该交给引擎的东西交了出去：URL 被翻成中文、{count} 占位符被译掉、 v1.2.3 变成 v1.2.3版、代码标识符被改大小写。 换引擎治不了 —— 这是任何机器翻译都会做的事。

做法是在提交之前把这些片段摘出原文，用私有区字符包一个编号占位： U+E000 + 36 进制编号 + U+E001。选私有区（U+E000–U+F8FF）的原因很直接： 这一段码位不属于任何自然文字的字符集，任何引擎都不会去改写它， 也不会把它当成单词切分或大小写折叠。引擎返回后按表还原。

保护哪些片段（14 类）

URL（含 mailto:）· 邮箱 · {{var}} / {var} / ${var} 模板占位符 · %s / %1$s 格式符 · 版本号 · 颜色值 · 长哈希 · 多段路径 · 文件名 · USER_ID 风格常量 · 驼峰函数名 · 下划线名。

模式表里有两处顺序与阈值是刻意的，都源于误保护： 路径模式必须排在文件名模式之前（否则 src/utils/helper.js 会被拆成两个占位符， 中间的 / 交给引擎就等着被吃掉）； 路径要求至少 2 个斜杠（input/output、and/or 这类是真英文，该翻）。 术语替换用捕获前缀 (^|[^A-Za-z0-9_]) 代替后行断言，避免某些环境下 lookbehind 不可用。

三条还原纪律

纪律具体做法违反之后会发生什么
① 正则必须要求至少一个哨兵在场 还原只认「哨兵 + 编号 + 哨兵」的完整形式，不接受「编号裸奔」 如果写成「编号两侧哨兵都可选」，那么译文里的普通数字会被当成编号去查表替换。 这条是最凶的：静默、且越修越错 —— 修完看到的还是「翻译不正确」
② 还原失败绝不泄漏哨兵 编号越界 / 无表 / 表项缺失时，把哨兵连同编号一起抹掉，再降级清理裸露哨兵 用户会在译文里看到不可见的私有区字符。后果不是「难看」而是文本被污染： 复制出去、存进数据库、再喂给别的程序，都会带着它
③ 占位符数量守恒 还原前比对「原文里的占位符数」与「译文里的占位符数」，对不上就判 bad 对不上说明引擎合并或拆分了条目，还原会把片段安到错的位置。 这一条不进缓存 —— 宁可下次重翻，也不把错的结果固化下来

第三条那个「不进缓存」是这整块设计里最有分量的决定： 缓存的作用是「同样的输入不必再问一遍」，而这里的前提正是「这次的结果不可信」。

怎么测「还原正则没写宽」——用反证，而不是用正例

正例（https://a.com/x 被正确还原）在正则写宽时照样通过。 所以 tools/test-protect.mjs 里最关键的一条是反证式的： 

输入：  第 1 章共 3 节
表：    { 0: "https://a.com/x" }          ← 表里只有编号 0
要求：  输出必须逐字等于「第 1 章共 3 节」

// 若还原正则写成「两个哨兵都可选」：
//   「1」被当成编号 0 … 不，「3」被查表命中 → 变成
//   「第 1 章共 https://a.com/x 节」  ← 静默错误，测试立刻红

这条断言的作用不是「确认功能可用」，而是确认判据有牙齿 —— 它专门构造了一个「正则写宽就会错、写对就没错」的输入。

术语表：把「不该被翻的专有名词」交给用户决定

掩码解决的是机器认得出的片段（URL、占位符、版本号…）， 但有一类只有用户知道：产品名、内部代号、希望统一译法的术语。 设置页「译文准确性」卡片里因此加了一张术语表，写法直接、无需文档： 

Acme Corp = 阿克米公司      ← 左侧一律替换成右侧
SLA = 服务等级协议
Widget =                    ← 右侧留空 = 保持原文，一个字母都不动
# 以 # 开头的整行是注释，不参与替换

术语表的替换与掩码走的是同一条链：先把术语命中的位置也摘成占位符， 引擎只能看到占位符，返回后再统一还原。这样术语不会在引擎内部被二次翻译 —— 如果只是「先替换成中文再送进去」，中文目标语下引擎会把它原样返回， 但在其它目标语言下，这段中文会被再翻一遍，等于术语表失效。 解析用「先找 =>、再找 =、最后找制表符」的三级降级，保证 parseGlossary / formatGlossary 严格互逆（读写一轮不改变内容）。

开关 protectUntranslatable（默认开）可以整体关掉掩码链。 关掉之后术语表也一并失效 —— 两者共用同一条链，不存在「只关一半」的状态。

前四条判据的牙齿靠「换个错的实现就报红」证明。S5 不行 —— 它不是靠几何量报红的，得换一种证明方式：先造出失败，再证明修复只影响了这一点。

6.4 一条走过的弯路：判据一开始没有牙齿

第一版判据只比「结构 + 宽度」。结果很可疑：inside 只报出 9 条内联高度变化， 而 sibling 在「容器自身就是单元」的夹具上只是「容器变高」—— 完全测不出截图里那个「标签被挤成一根竖条」。

  1. chips 夹具加 width:420px —— 制造空间压力，译文才「无处可去」。
  2. 新增 textrow 夹具：display:flex 的行里放块级 <p>， 兄弟插入会平分三列宽度 → 立刻报出 9 条宽度变小。
  3. 新增 S4 判据「译文宽度 < 宿主宽度 60% 即被压扁」。

补完之后：inside 报 3 条挤扁（最窄 40px）、sibling 报 18 条挤扁 + 9 条宽度变小， auto 全 0。断言终于咬住了。

最初定的 90% 会误报 9 条 —— 表格单元格有内边距，译文本来就只有内容区那么宽， 90% 的阈值把「正常的内边距」也算成了「被压扁」。降到 60% 之后 auto 归零，而 inside 在 chips 上的 40px（≈ 宿主 13%）依然被抓到。 阈值要卡在「误报」与「漏报」中间那条线上，不是越严越好。

v1.6.0 抓到的那一个：一个恒为 false 的守卫

裁切分支写完、测试也写得漂亮，真机基准却报出 clippedTrans = 6 / rescuedFromClip = 0 —— 分支一次都没生效过。 守卫写的是 clipAnchor !== el && !clipAnchor.contains(el)， 而 safeAnchor 是「向上求锚点」，返回的必然是 el 的祖先， 祖先当然 contains(el) —— 条件恒为 false。

教训：「分支被覆盖到了」和「分支生效了」是两件事。 前者靠行覆盖率的数字就能确认，后者只能靠那个分支改变了什么可观测的量。 所以 rescuedFromClip / clippedTrans 这两个计数留在了基准里、每次跑都报 —— 它们就是这条分支的「活体检测」。

另一条纪律：不要写自欺式断言

曾写出 eq('子元素个数没变', row.children.length, rowKidsBefore + 1 - 1 + 0 + 1 - 1) —— 右侧恒等于 2，这条断言永远不会失败。正确写法是直接写期望字面量 2。 表达式的复杂度不等于断言的强度。

v1.6.0 写裁切测试时又踩到同一类的两个变种，都记在这里：

  • 用 className 全等去比译文块 —— 译文块的类名是 ct-trans ct-trans--out ct-s-plain 这种多值串，全等必然 false。 应该查 classList.contains('ct-trans--out')。
  • 沿子树找译文 —— 裁切容器的译文插在容器之后，是兄弟关系， 用 querySelector 在容器内部找永远找不到。 要先断言长度再索引，否则后面一行会抛 TypeError，把断言失败伪装成崩溃。

这两处的共同点：断言写错的时候，测试报的是「失败」，但失败的原因不是产品的缺陷。 必须回读测试本身，才能区分「产品坏了」和「判据写歪了」。

SECTION 07性能账：冷启动与稳定态分离

7.1 单次采样等于噪声

「读一次 getComputedStyle 要多花 3.5 ms」这个结论曾经被误读。 最初测出 inside 0.8 ms vs auto 3.5 ms，看起来像「慢了 4 倍」。 但单次采样里混着三件不相干的事：样式首次失效、JIT 预热、GC。

修正办法是同进程交替测量，并且把「冷启动一次性成本」与 「稳定态边际成本」分开报：

方式采集（冷 · 两次复跑）采集（温 · 两次复跑）读数
智能分流 auto4.7 / 3.7 ms1.7 / 0.7 ms首次读样式，付一次整页样式重算
inside（不读样式）1.3 / 0.8 ms1.3 / 0.8 ms基线
净成本≈ 3.0 ms 一次性≈ 0 ms（噪声内）稳定态不花钱

两次复跑的绝对值有波动（这台机器上 collect 单次抖动可以到 ±1 ms）， 但「冷 − 温」这个差值在两次里都恰好是 3.0 ms —— 这说明波动来自环境，不是来自改动本身。

为什么稳定态几乎为零

因为决策缓存在 WeakMap 里，并且只在采集阶段读。 同一元素在后续轮次（已译态重扫、变更后重扫）直接命中缓存，一次 getComputedStyle 都不发。

8.2 已知边界

  • 段落自身变高无法避免。这是「下方双语」这个形态的固有代价 —— 承载译文的元素变高是设计要求的，不是 bug。要彻底不变高只能换成「仅显示译文」或「悬停查看」。
  • 站点级特殊布局仍可能有例外。夹具覆盖了 13 类典型宿主 / 39 个夹具， 不等于覆盖了所有真实站点。判据的价值在于：出问题时能定位到是哪一条， 而不是靠肉眼判断。
  • 冷启动固定付约 3 ms。首次进入页面时读一次样式需要一次整页样式重算。 这是在 2500 块页面上测的，小页面基本感知不到。 另外 clipInfo() 的祖先上溯（最多 6 层）不进 WeakMap 缓存 —— 裁切状态会随站点交互变化，缓存会让「展开全文之后再翻」拿到过期结论。这是用一点重复遍历换正确性。
  • 闸门是启发式。阈值（标签占比 20%、标签数 3、长度 24、": 计数 4） 是经验值，可能对极端文本误判。闸门只影响「翻不翻」，不会破坏页面结构， 因此误判的代价是可控的。
  • 掩码表只覆盖可枚举的模式。14 类片段靠正则识别，认不出来的「专有名词」需要用户 自己加进术语表。术语表本身是逐条字符串替换，不做词形变化 —— 英文里 Widgets 与 Widget 是两个不同的匹配目标， 需要用户各写一行（或者接受后者匹配到前者前缀，再靠右边界约束）。这一点在设置页里有说明文案。
  • 裁切判定只认「自己会不会被裁」，不预测站点行为。 clipsContent 读的是当下的 computed style。 如果站点用 JS 在滚动时动态加 max-height，第一次采集时判定不到， 译文会留在容器里。要覆盖这种情况需要 MutationObserver 持续跟踪样式变化， 成本远大于收益（会引入持续的重判循环）。
  • sibling 强制模式保留但不应作为默认。 它会让 1475 / 2250 个单元的相邻兄弟关系失效。它存在的意义是排障对照。
